## 1. เสร็จคืออะไร (ตรวจได้)

- โปรเจคประเภทซอฟต์แวร์เดิน flow เต็มบนเบราว์เซอร์ได้: สร้างงานแบบมีชนิดและแต้ม → ลากเข้ารอบ → เริ่มรอบ → ย้ายงานบนบอร์ด → ปิดรอบโดยย้ายงานค้างไปรอบถัดไป → ออกเวอร์ชันได้ changelog (e2e ที่ 3 ขนาดจอ สว่าง/มืด)
- กราฟงานคงเหลือตรงกับแต้มที่ยังไม่เสร็จ ณ สิ้นแต่ละวัน และความเร็วทีมตรงกับแต้มที่เสร็จต่อรอบ (test ด้วยข้อมูลตั้งต้นที่รู้คำตอบล่วงหน้า)
- เลขงานไม่ซ้ำแม้สร้างพร้อมกัน และไม่ถูกใช้ซ้ำหลังลบ (test ยิงพร้อมกัน)
- ผูกงานขวางเป็นวงไม่ได้ ทั้งวงตรง (A↔B) และวงยาว (A→B→C→A) (test)
- เริ่มรอบที่สองขณะรอบแรกยังไม่ปิดไม่ได้ แม้สองคำขอมาพร้อมกัน (test + ข้อจำกัดใน DB)
- โปรเจคประเภทอื่นหน้าตาและพฤติกรรมไม่เปลี่ยน (test เดิม 621 ตัว + e2e เดิม 382 ข้อผ่าน)
- migration รันซ้ำได้ และ replay บนสำเนาข้อมูลแล้วค่าเดิมไม่เปลี่ยน

## 3. ร่างแบบ: ข้อมูลของกราฟงานคงเหลือ (D-7)

กราฟต้องรู้ "แต้มที่ยังไม่เสร็จ ณ สิ้นวันที่ X" ของวันที่ผ่านไปแล้ว ซึ่งค่าปัจจุบันของงานบอกไม่ได้ (งานที่เสร็จวันนี้ เมื่อวานยังไม่เสร็จ)

### แบบ A: บันทึกยอดรายวันของรอบ (แนะนำ)
ตาราง `project_sprint_days(sprint_id, day, scope_points, done_points)` ทุกครั้งที่งานในรอบเปลี่ยน (ย้ายคอลัมน์ แก้แต้ม เพิ่ม/เอาออกจากรอบ) คำนวณยอดของรอบใหม่จากงานจริงแล้ว upsert แถวของ "วันนี้ตามเวลาเซิร์ฟเวอร์" วันที่ไม่มีการเปลี่ยนใช้ค่าของวันก่อนหน้า
- ได้: อ่านกราฟเป็น query เดียว ค่าในแต่ละวันคำนวณจากงานจริงทุกครั้ง จึงไม่สะสมความคลาดเคลื่อน test ง่าย (ใส่แถวตั้งต้นแล้วดูผล)
- เสีย: ย้อนแก้อดีตไม่ได้ (ถ้าบันทึกพลาดวันไหน วันนั้นผิดถาวร) และรอบที่เริ่มก่อนมี P1 ไม่มีข้อมูล (ไม่มีอยู่แล้ว เพราะรอบเพิ่งมีใน P1)

### แบบ B: บันทึกเหตุการณ์แบบมีโครงสร้าง แล้วคำนวณย้อน
ตาราง `project_task_events(task_id, field, old, new, at)` กราฟคำนวณโดยเล่นเหตุการณ์ซ้ำตั้งแต่วันเริ่มรอบ
- ได้: ย้อนคำนวณใหม่ได้ ใช้ทำรายงานอื่นในอนาคตได้ (เช่น เวลาที่งานค้างในแต่ละคอลัมน์)
- เสีย: logic เล่นซ้ำซับซ้อน (งานเข้า-ออกรอบ แต้มเปลี่ยนกลางทาง) ต้องเก็บเหตุการณ์ทุกจุดที่แก้งาน พลาดจุดเดียวกราฟเพี้ยนแบบหาสาเหตุยาก

แนะนำ A: เป้าของ REQ-S5 คือกราฟถูกต่อวัน ไม่มีรายงานอื่นในสเปกที่ต้องใช้เหตุการณ์ละเอียด

## 4. ร่างแบบ: งานใหญ่ งานลูก และงานย่อย (D-8)

ความสัมพันธ์มีสองชั้น: งานใหญ่ ← เรื่องผู้ใช้/งาน/บั๊ก ← งานย่อย

### แบบ A: คอลัมน์ `parent_id` เดียว (แนะนำ)
งานลูกของงานใหญ่ชี้ไปที่งานใหญ่ งานย่อยชี้ไปที่งานแม่ กฎในโค้ด: งานย่อยต้องมีแม่ที่ไม่ใช่งานใหญ่หรืองานย่อย, งานอื่นมีแม่ได้เฉพาะงานใหญ่
- ได้: คอลัมน์เดียว query งานลูกแบบเดียวกันทุกชั้น
- เสีย: งานย่อยไม่ผูกกับงานใหญ่ตรง ๆ (ต้องผ่านแม่ 2 ชั้น) ใช้ JOIN หนึ่งชั้นตอนนับ % ของงานใหญ่

### แบบ B: สองคอลัมน์ `epic_id` และ `parent_id`
- ได้: กรองตามงานใหญ่ได้ตรง รวมงานย่อย
- เสีย: ค่าสองคอลัมน์ต้องตรงกันเสมอ (งานย่อยต้องมี epic เดียวกับแม่) ย้ายแม่ไปงานใหญ่อื่นต้องอัปเดตงานย่อยตาม พลาดแล้วข้อมูลขัดกันเอง

แนะนำ A: กฎ "งานย่อยอยู่งานใหญ่เดียวกับแม่" เป็นจริงเองโดยโครงสร้าง ไม่ต้องดูแล

## 5. แบบที่เหลือ (ตัดสินเอง ย้อนได้ ทักได้)

- **เลขงาน:** `projects.key_prefix` (อังกฤษ 2–6 ตัว), `projects.next_task_number`, `project_tasks.number` + UNIQUE(project_id, number) ออกเลขใน lock ของโปรเจค ตัวนับเพิ่มอย่างเดียว เลขจึงไม่กลับมาใช้ซ้ำ backfill เลขให้งานเดิม**ทุกประเภท**เรียงตาม id (เปลี่ยนประเภทเป็นซอฟต์แวร์ทีหลังจะมีเลขทันที) แต่แสดงเฉพาะซอฟต์แวร์ ตัวย่อตั้งต้นสร้างจากชื่อโปรเจค (ตัวอักษรอังกฤษ 2–4 ตัวแรก ไม่มีให้ใช้ `P`) ค้น "DF-49" แปลงเป็น number = 49
- **ชนิดงานและแต้ม:** `project_tasks.kind` enum(epic, story, task, bug, sub) ค่าตั้งต้น task, `story_points` tinyint NULL, `projects.point_scale` enum(fib, ten) งานใหญ่ไม่มีแต้มของตัวเอง (รวมจากงานลูก) และไม่ขึ้นบอร์ด
- **รอบงาน:** `project_sprints(name, goal, start_date, end_date, state planned/active/closed, committed_points, completed_points, started_at, closed_at)` รอบที่กำลังทำมีได้หนึ่งรอบ: คอลัมน์คำนวณ `active_project = IF(state='active', project_id, NULL)` + UNIQUE จึงกันได้ถึงระดับ DB แม้สองคำขอพร้อมกัน `project_tasks.sprint_id` (NULL = คลังงาน), `backlog_rank` สำหรับลำดับในคลัง งานย่อยอยู่รอบเดียวกับแม่เสมอ (ย้ายแม่ = ย้ายงานย่อย)
- **สวิตช์รอบงาน:** `projects.use_sprints` ค่าตั้งต้น 1 ปิดแล้วบอร์ดแสดงทุกงาน ซ่อนแท็บคลังงานและกราฟงานคงเหลือ ข้อมูลรอบไม่ลบ
- **ปิดรอบ:** งานเสร็จคงผูกรอบเดิม (ใช้คิดความเร็ว) งานค้างไปรอบถัดไปที่วางแผนไว้ หรือคลังงาน ถ้าไม่มีรอบถัดไป ตัวเลือกแรกคือ "สร้างรอบใหม่แล้วย้ายเข้าไป" `committed_points` บันทึกตอนเริ่มรอบ `completed_points` ตอนปิด
- **กราฟนับทุกวันรวมเสาร์-อาทิตย์** (สเปกเขียน "ต่อวัน") เส้นแบนในวันหยุดเป็นเรื่องปกติ ถ้าทีมไม่ทำงานวันหยุดเยอะ ค่อยเพิ่มตัวเลือกข้ามวันหยุด
- **เวอร์ชัน:** `project_releases(name, release_date, state planned/active/released, released_at, changelog)` `project_tasks.release_id` changelog สร้างตอนกด "ออกเวอร์ชัน" แล้ว**เก็บเป็นข้อความ** แก้ได้ ชื่องานที่แก้ทีหลังไม่ทำให้ changelog ที่ออกไปแล้วเปลี่ยน จัดกลุ่ม: story = ของใหม่, task = ปรับปรุง, bug = แก้บั๊ก
- **แผนงาน:** เพิ่ม `project_tasks.start_date` ใช้กับงานใหญ่ (วันจบใช้ `due_date` เดิม) ลากแถบแล้ว PATCH ทั้งสองวัน
- **งานขวาง:** `project_task_blocks(blocker_id, blocked_id)` งานในโปรเจคเดียวกันเท่านั้น ก่อนผูกค้นจากงานที่จะถูกขวางตามเส้นทางทั้งหมดใน lock ของโปรเจค ถ้าไปถึงงานต้นทางได้คือเป็นวง ปฏิเสธพร้อมข้อความ (EDGE-S1) ป้าย "ติด" = มีงานที่ต้องรออยู่นอกกลุ่ม done
- **ลิงก์ภายนอก:** `project_task_links(task_id, url, label)` รับเฉพาะ `http:` และ `https:` (กัน `javascript:` ที่กดแล้วรันโค้ด) ตัดความยาว 2,000 ตัว
- **ส่วนของระบบ:** `project_components(project_id, name)` + `project_task_components(task_id, component_id)` ชื่อไม่ซ้ำในโปรเจคเทียบแบบ `utf8mb4_bin` และแปลง NBSP ก่อน TRIM (กฎใน CLAUDE.md)
- **ช่องบั๊ก:** `severity` enum (critical/high/medium/low) เป็นคอลัมน์เพราะต้องกรอง, `repro_steps` `expected` `actual` `environment` เป็นคอลัมน์ข้อความ NULL ได้
- **แขกลิงก์แชร์ (ตาม D-5):** เห็นชนิด เลขงาน แต้ม รอบ แผนงาน เวอร์ชัน ไม่เห็นลิงก์ภายนอกและรายละเอียดบั๊ก (ขั้นตอนทำซ้ำ สภาพแวดล้อม) เพราะมักเป็นข้อมูลภายใน
- **เปลี่ยนประเภทออกจากซอฟต์แวร์:** เตือนเมื่อมีรอบกำลังทำหรือเวอร์ชันที่ยังไม่ออก ข้อมูลทั้งหมดอยู่ครบ เปลี่ยนกลับมาก็เห็นเหมือนเดิม (EDGE-P5)
- **API ที่รับ id** (รอบ เวอร์ชัน ส่วนของระบบ งานขวาง ลิงก์) ตอบเหมือนกันทั้ง id ของโปรเจคอื่นและ id ที่ถูกลบ (กฎใน CLAUDE.md)

## 8. ความเสี่ยง

- **backfill เลขงานบนข้อมูลจริง:** ต้องไม่ชน UNIQUE และรันซ้ำแล้วไม่เปลี่ยนเลขเดิม → backfill เฉพาะแถวที่ `number IS NULL` ภายใต้เงื่อนไขเดียวกับการเพิ่มคอลัมน์ และ replay บนสำเนาข้อมูลก่อน
- **stack สาม PR:** ถ้า P0a/P0b ถูกขอแก้ ต้อง rebase P1 ตาม migration 042 ต้องเป็นเลขถัดจาก 041 เสมอ
- **ไฟล์ JS โตเกิน:** `projects-team.js` 595 บรรทัด `projects-views.js` 534 บรรทัด ส่วนของซอฟต์แวร์แยกเป็นไฟล์ใหม่ (`projects-software.js` และ `projects-roadmap.js`) โหลดเฉพาะโปรเจคซอฟต์แวร์
- **ลากบนมือถือ:** คลังงานและแผนงานใช้ pointer events ให้ใช้ได้ทั้งเมาส์และนิ้ว มีทางสำรองที่ไม่ต้องลาก (ช่องรอบงานและช่องวันที่ในรายละเอียดงาน)
