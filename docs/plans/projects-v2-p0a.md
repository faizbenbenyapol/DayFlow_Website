## 3. ร่างแบบ: คอลัมน์ที่ตั้งเองได้ (เรื่องเดียวที่ย้อนยาก)

ทั้งสองแบบใช้ตารางใหม่เหมือนกัน:

```sql
project_columns (id, project_id, name VARCHAR(60), grp ENUM('todo','doing','done'), position, created_at, updated_at)
project_tasks.column_id  INT UNSIGNED NULL → FK project_columns(id)
projects.type            ENUM('general','software','marketing','finance') NOT NULL DEFAULT 'general'
```

ฝั่งผู้เรียก (โค้ดที่ controller จะเขียน):

```php
$col = ProjectColumn::findInProject($projectId, $columnId);   // null ถ้าไม่ใช่ของโปรเจคนี้ → 404 แบบเดียวกันทุกกรณี
ProjectTask::moveTo($taskId, $projectId, $col, $position);    // ย้ายงาน = เปลี่ยนคอลัมน์ + ตำแหน่ง ในที่เดียว
ProjectColumn::delete($projectId, $columnId, $moveToId);      // ย้ายงานก่อนลบ ใน transaction เดียว ปฏิเสธถ้าเป็นคอลัมน์สุดท้ายของกลุ่ม
```

### แบบ A: `status` เดิมเป็นเงาของกลุ่ม (แนะนำ)

- `column_id` คือความจริงเดียว `status` เดิมยังอยู่ และ **ถูกเขียนโดย `ProjectTask::moveTo` ที่เดียว** ตามกลุ่ม: done → `Done`, todo → `To Do`, doing → `In Progress` (งานที่ย้ายมาจาก "รอตรวจ" เดิมคง `Review`)
- ผู้อ่านที่ถามแค่ "เสร็จหรือยัง" (แดชบอร์ด นับความคืบหน้า หน้าวันนี้) **ไม่ต้องแก้** เพราะ `status = 'Done'` ตรงกับกลุ่ม done เสมอ
- ถ้าต้องถอย deploy กลับเป็นโค้ดเก่า โค้ดเก่ายังอ่าน `status` ได้ บอร์ดเก่ายังแสดงงานครบ
- ข้อเสีย: ข้อมูลเก็บสองที่ ถ้าใครเขียน `status` ตรง ๆ จะไม่ตรงกับ `column_id` กันด้วย: (1) มีแค่ `moveTo` ที่เขียน (2) test ที่ไล่ทุกแถวว่า `status` ตรงกับกลุ่มของคอลัมน์ (3) เฟสถัดไปที่ไม่ต้องการถอยแล้วค่อยเลิกใช้ `status` (expand → contract)

### แบบ B: เลิกใช้ `status` ทันที

- ผู้อ่านทั้ง 9 ไฟล์เปลี่ยนไป JOIN `project_columns` แล้วดู `grp` ลบ `status` ใน migration ถัดไป
- ข้อดี: ข้อมูลที่เดียว ไม่มีโอกาสไม่ตรงกัน
- ข้อเสีย: diff ใหญ่ขึ้นราว 2 เท่า แตะแดชบอร์ดและหน้าวันนี้ซึ่งไม่เกี่ยวกับ P0a และถอยกลับไปโค้ดเก่าไม่ได้หลังลบ `status`

### ที่พิจารณาแล้วไม่เลือก

- เก็บคอลัมน์เป็น JSON ใน `projects`: นับความคืบหน้าและกรองด้วย SQL ยาก (ต้อง `JSON_TABLE`) และลบคอลัมน์ที่มีงานต้องเขียนสองที่

**คำแนะนำ: แบบ A** เพราะ P0a แตะข้อมูลจริงและเป็นฐานของอีก 4 เฟส การถอยกลับได้มีค่ากว่าความเรียบของแบบ B ส่วนเงา `status` จะถูกเก็บกวาดเมื่อเจ้าของลอง P0a แล้วพอใจ

## 4. บทบาท (ตัดสินเองได้ เพราะผู้ใช้ไม่เห็นความต่าง และย้อนได้)

- ค่าในฐานข้อมูล: `Admin` (ใหม่), `Editor` (แสดงเป็น "สมาชิก"), `Viewer` (แสดงเป็น "ดูอย่างเดียว") เจ้าของยังเป็น `projects.user_id` **ไม่แปลงข้อมูลเดิม** สมาชิกเดิมจึงเป็น "สมาชิก" ทันทีตาม REQ-P7 และลิงก์แชร์ที่ใช้ `share_role` เดิมไม่ต้องแตะ
- เช็กสิทธิ์ที่เดียว: `requireRole($project, 'member'|'admin'|'owner', $action)` เทียบลำดับ Owner 4 > Admin 3 > Editor 2 > Viewer 1 ค่าที่ไม่รู้จักได้ 0 (ปิดไว้ก่อน เหมือนที่ `requireEditor` ทำตอนนี้) แล้วลบ `requireEditor`/`requireOwner` ออก เพื่อไม่ให้มีสองวิธีเช็กสิทธิ์
- ผู้ดูแลเชิญคนได้ เอาสมาชิก/ดูอย่างเดียวออกได้ ตั้งใครเป็นผู้ดูแลหรือเอาผู้ดูแลออกไม่ได้
- เอาคนออก: งานที่เขารับผิดชอบกลายเป็นว่าง ใน transaction เดียวกัน (EDGE-P3) ส่วนแจ้งเตือนเจ้าของรอระบบแจ้งเตือนใน P0b (REQ-P10)

## 6.1 สมมติฐานที่ใช้ (ตัดสินเอง ย้อนได้ รอเจ้าของทักถ้าไม่ตรง)

- ชื่อคอลัมน์ 1–60 ตัวอักษร ห้ามซ้ำในโปรเจคเดียวกัน สูงสุด 12 คอลัมน์ต่อโปรเจค
- เปิด/ปิดลิงก์แชร์เป็นการตั้งค่าโปรเจค ผู้ดูแลทำได้ (เดิมเจ้าของเท่านั้น) ลิงก์แชร์เป็นได้แค่ สมาชิก/ดูอย่างเดียว
- คอลัมน์เรียงตามกลุ่มเสมอ (ยังไม่เริ่ม → กำลังทำ → เสร็จ) เรียงได้ภายในกลุ่ม ตรงกับ mockup แบบ A
- ย้ายคอลัมน์ข้ามกลุ่มหรือลบคอลัมน์แล้วย้ายงาน ไม่เปลี่ยนเวลาแก้ไขล่าสุดของงาน (ผู้ใช้แก้คอลัมน์ ไม่ได้แก้งาน)
- client เดิมที่ส่ง `status` ยังใช้ได้: To Do → คอลัมน์แรกของ todo, In Progress → คอลัมน์แรกของ doing, Review → คอลัมน์สุดท้ายของ doing, Done → คอลัมน์แรกของ done

## 7. ความเสี่ยงและทางถอย

- migration แตะข้อมูลจริง: deploy ต้องสำรอง DB ก่อน (เป็นงานของเจ้าของ) แบบ A ถอยโค้ดได้โดยไม่ต้องถอย DB — เมื่อกลับมาโค้ดใหม่ต้องรัน `migrate.php --force` ก่อนมีคนใช้ (038 ขั้น 4b ให้ status ที่โค้ดเก่าเขียนชนะ) ตามผลผู้ตรวจอิสระรอบ 2
- ผู้ดูแล (`Admin`) ภายใต้โค้ดเก่าจะถูกมองเป็นค่าที่ไม่รู้จัก → ดูอย่างเดียว (ปิดไว้ก่อน) ไม่มีใครได้สิทธิ์เกิน
- ถ้าเคยถอยโค้ดหลัง migrate แล้วกลับมาใช้โค้ดใหม่: โปรเจค/งานที่โค้ดเก่าสร้างระหว่างนั้นจะไม่มีคอลัมน์ ให้รัน `php scripts/migrate.php --force` หนึ่งครั้ง (038 เก็บให้ครบเองด้วยเงื่อนไขระดับแถว — พิสูจน์แล้ว 2026-11-24 บนฐานทดสอบ: 18 โปรเจค 15 งาน → 0)
- สถานะเงาเป็นฟังก์ชันของคอลัมน์ล้วน: done → Done, todo → To Do, doing คอลัมน์สุดท้าย → Review, doing อื่น → In Progress (เปลี่ยนจากกฎเดิมที่ขึ้นกับประวัติงาน เพราะบอร์ดเดิมวาดงานผิดคอลัมน์ — เจอตอนลองบอร์ดจริง slice 3)
- บอร์ดที่มีคอลัมน์ 5+ บนมือถือ: เลื่อนแนวนอน ตาม mockup
