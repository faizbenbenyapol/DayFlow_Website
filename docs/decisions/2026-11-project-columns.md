# การตัดสินใจ: คอลัมน์ของโปรเจคที่ตั้งเองได้ และบทบาท 4 ระดับ (P0a)

สถานะ: เจ้าของยืนยันแล้ว 2026-11-24
รายละเอียดร่างทั้งสองแบบ ลำดับงาน และวิธีตรวจ: `docs/plans/projects-v2-p0a.md` หัวข้อ 3–4

## ตัดสินอะไร

1. **คอลัมน์เก็บในตาราง `project_columns`** (ชื่อ, กลุ่ม `todo/doing/done`, ลำดับ) งานชี้คอลัมน์ด้วย `project_tasks.column_id` ซึ่งเป็นความจริงเดียว
2. **`project_tasks.status` เดิมเป็นเงาของกลุ่ม** (expand → contract) เขียนโดย `ProjectTask::moveTo` ที่เดียว ผู้อ่านเดิม (แดชบอร์ด นับความคืบหน้า) ไม่ต้องแก้ และถอยโค้ดได้โดยไม่ถอย DB จะเลิกใช้ `status` ในเฟสหลังเมื่อเจ้าของลอง P0a แล้ว
3. **บทบาทไม่แปลงข้อมูลเดิม** ค่าในฐานข้อมูลเป็น `Admin` (ใหม่) / `Editor` (แสดง "สมาชิก") / `Viewer` (แสดง "ดูอย่างเดียว") เจ้าของคือ `projects.user_id` เช็กสิทธิ์ที่ `requireRole()` จุดเดียว ค่าที่ไม่รู้จักถือว่าไม่มีสิทธิ์

## ไม่เลือก และทำไม

- เลิกใช้ `status` ทันที (แบบ B): diff ใหญ่ขึ้นราว 2 เท่า แตะหน้าที่ไม่เกี่ยว และถอยไม่ได้หลังลบคอลัมน์
- เก็บคอลัมน์เป็น JSON ใน `projects`: นับและกรองด้วย SQL ยาก ลบคอลัมน์ที่มีงานต้องเขียนสองที่
- แปลง `Editor` เป็น `Member` ในฐานข้อมูล: ต้องแตะแถวจริงและ `share_role` ของลิงก์แชร์ โดยผู้ใช้ไม่เห็นความต่าง

## ผลที่ตามมา

- มีข้อมูลสองที่ชั่วคราว (`column_id` กับ `status`) กันไม่ให้แยกกันด้วย writer เดียวและ test ที่ไล่ทุกแถว
- โค้ดเก่า (ถ้าถอย deploy) มองผู้ดูแลเป็นค่าที่ไม่รู้จัก → ดูอย่างเดียว ไม่มีใครได้สิทธิ์เกิน
